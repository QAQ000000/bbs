# Worker 背压与资源隔离

核对日期：2026-09-27。当前为单实例 Go API + PostgreSQL，业务请求与后台任务共享连接池。本文区分已实现机制、实际压测证据与后续候选方案；候选方案不是已上线功能，也不是现有配置项。

## 已实现机制

| 消费者 | 当前调度 | 当前边界 |
| --- | --- | --- |
| 经验/积分、称号 | 每秒调度；每轮最多 10 个事务、250ms 软预算；成长单批 100、称号单批 50；10 秒上下文 | 开始下一批前检查共享池占用，达到 75% 则让出本轮；持续前台压力可能延长任务等待 |
| 版块统计 | 每秒调度；每轮最多 10 批、250ms 软预算；10 秒上下文；共享池 75% 占用时让出 | 单次重算随版块数据增长；预算只在事务之间检查 |
| 搜索 | 每 250ms 调度；每轮最多 10 个事件、250ms 软预算；10 秒上下文 | 没有与成长相同的池占用门槛；前台搜索查询与后台索引写入是不同负载，不能混为一谈 |
| 订阅 | 每秒调度；每轮最多 100 批、250ms 软预算；10 秒上下文；单批最多 50 名候选用户 | 含权限复核、提及/回复优先级、持久投递；在线计数按轮次合并，离线收件人不查询实时未读数 |
| 邮件 | 2 个消费协程；任务租约、退避与最多 8 次自动尝试；周期维护 | SMTP 接收与数据库确认之间存在至少一次投递边界；不可用扩大连接池替代投递幂等策略 |
| 积分榜/站点快照 | 启动及每小时刷新；共用 30 秒上下文 | 没有专门的重试队列、错峰调度或独立资源池；当前故障矩阵不覆盖小时级刷新恢复 |

250ms 是事务之间的让出预算，不是 SQL 超时，也不代表一轮必定在 250ms 内完成。所有消费者仍受其上下文截止时间约束。现有六类持久任务已通过 [12 项故障恢复演练](WORKER_RECOVERY.md)，这与持续容量是两类独立证据。

## 如何决定下一项优化

同时看固定到达速率、HTTP 错误/漏发、P95/P99、队列最老年龄和增长趋势、连接池等待、数据库 CPU/I/O、锁等待与最终一致性。只有一个瞬时队列长度不足以决定扩容或拆池。

| 实际观察 | 优先动作 | 预期作用与代价 |
| --- | --- | --- |
| 目标请求全部完成，队列年龄稳定且停压能及时清空，池等待低 | 保持当前共享池和批处理；完善真实流量与大数据验收 | 保留现有简单性；不把缺少的验收结果包装成性能问题已永久解决 |
| 前台连接等待上升，后台长事务占池，但数据库仍有余量 | 试验总连接预算内的前台/后台分池 | 改善资源公平性；要证明前台尾延迟下降且后台不饥饿，不能只展示读取更快 |
| 前台压力使有占用门槛的消费者长期不运行 | 在全局后台并发上限内设计有界进度保障 | 限制最老任务等待；代价是保留少量后台执行机会，需要同时约束前台入口负载 |
| 数据库 CPU 接近可用上限，连接本身不紧张 | 先定位慢查询指纹、读路径开销与搜索模式，控制高成本查询并发 | 降低总工作量；新增连接或 Worker 数并不消除这些计算 |
| 持续物理写入/同步等待增加，伴随请求或队列延迟 | 结合实际存储、检查点与 WAL 指标做单变量 PG 配置试验 | 只报告复测收益；不在业务库关闭 fsync 或同步提交来制造测试提升 |
| 某类队列单独积压而 CPU/连接都有余量 | 先优化该类批处理，再评估独立消费者并发 | 并行度受业务锁、排序、去重、权限复核约束；不直接删除这些约束 |
| 周期快照错过刷新或读取到过旧快照 | 增加明确的重试、生成时间/数据时间及过期状态 | 改善时效和可诊断性；与站点时区、保留期一起验收 |

## 如需分池，建议的最小边界

1. 先保持单进程、原 PostgreSQL 持久任务和完整事务。分别注入前台、后台连接依赖，限定两者连接数之和，不按每个队列各开一套默认大池。
2. 单独暴露两个池的等待、占用、取消和超时；根据同一压测对照选择预算，本文不预设未经测量的连接比例。
3. 不浅拷贝包含锁的 Store 或 Server。Store 含用户名缓存、首页缓存、浏览计数生命周期；Server 含 SSE Hub、限流器及配置状态。应明确这些状态的所有权，共用实时通知 Hub，避免额外启动浏览计数或后台任务。
4. 分池后重新界定“75% 占用”的含义：后台池占用不能冒充前台压力指标，也不能因池变小使成长/称号一直让出。用真实池等待与最老任务年龄验证公平性。
5. 有界并发/背压必须在事务外生效，不持有用户、主题或队列行锁等待许可。数据库提交后才能发送实时提示；前台已成功写入的事件仍必须最终消费。
6. 用相同数据量、请求分布、总连接预算和持续时长对照，并复跑故障矩阵；同时检查权限、去重、经验积分账本、通知、搜索及计数一致性。

## 下一项试验：订阅有界连续消费

现有订阅消费者每秒启动一轮，单轮软预算 250ms。停压后实际观察到队列仍有数千条，但 PostgreSQL 只占约 0.2 个核心，连接池也有大量空闲；这是优先试验调度的依据，不足以单独证明高档发压时的积压全部来自调度。

建议先做单消费者的调度对照，保持持久事务和总连接预算：

1. 将一轮返回信息明确区分为空队列、达到预算、资源繁忙、失败和取消。现有返回的处理批次数不能直接等同于完成的事件数或成功通知数；一个事件可能跨多批投递。
2. 达到预算且资源允许时，在可取消的短暂让出后继续下一轮；空队列保持低频轮询，数据库失败采用有上限的退避。禁止无等待空转或在持锁事务中等待调度许可。
3. 保留单轮事务数量、时间软预算和 SQL 上下文上限，每轮发布已提交批次合并后的在线计数。继续保留权限复核、提及/楼层回复优先级及投递去重。
4. 每轮之间检查前台压力，繁忙时延后额外追赶；基础消费机会与额外追赶分开，避免持续压力下无限期跳过全部工作。池占用只能反映连接压力，不能代替数据库 CPU 饱和信号。
5. 先用相同 20/2 池和固定积压验证停压恢复速度，再按相同三档各 10 分钟对照。同时检查读取/回帖尾延迟、漏发、订阅最老年龄、其余队列、公平性与最终一致性；改善排空时间而恶化前台容量不能算全面通过。
6. 调度变更须补空队列、预算退出、资源繁忙、取消、错误退避及已提交批次发布的回归，并复跑现有进程/数据库故障矩阵。此处为实施方案，尚未修改生产调度，也没有预先承诺提升倍数。

## 本轮复测

在提交 `2fb3d91` 上，以 `20/2` 连接池完成三档各 10 分钟持续负载及自然排空；输入、采样及完整结果见 [持续负载验收](SUSTAINED_LOAD.md)，证据 `/tmp/gobbs-backend-results.wZ6KN1`。

- 200 读/秒 + 5 回帖/秒、400 读/秒 + 15 回帖/秒两档均达到所有计划到达量，没有 HTTP 错误。中档订阅峰值 74 条、最老年龄峰值 7.05 秒，没有持续增长；该结论仅适用于本次夹具和时长。
- 600 读/秒 + 30 回帖/秒档漏发 1,591 次读取，订阅峰值 13,619 条并持续增长，PG CPU 均值 5.23 核、最大 7.18 核（共 8 核）。前台回帖成功不代表下游通知时效达标，该档容量验收失败。
- 停压后约 543.4 秒自然排空，恢复期 PG CPU 均值约 0.21 核、池等待很低。最终 30,000 条新增回帖全部可索引，80,000 条帖子、600,000 条订阅通知和版块计数对账通过，两类快照存在，监控错误为 0。

因此下一项优先实施并对照上述订阅调度试验，另对高档搜索/读路径 CPU 做定点剖析；是否分池由前台等待与后台公平性证据决定。不立即扩大连接数、引入 Redis 或调整常驻 PG 参数。本阶段新增的是测量证据与方案，生产消费者调度未变，改善幅度须等后续同条件对照确认。
