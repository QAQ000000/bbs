## 已复现问题

### F01 / P1：邮箱换绑缺少重新验证，可绕过直接改密的旧密码要求

位置：`internal/api/handler_profile.go:55`、`internal/store/notify.go:331`。

现有流程是持有登录 Cookie 和 CSRF 即可调用 `PATCH /api/v1/me` 替换邮箱，随后新邮箱可以申请密码重置。新邮箱尚未验证也能进入重置邮件队列。

复现结果：不提交当前密码，更换邮箱返回 HTTP 200；使用新邮箱对应的重置令牌修改密码也返回 HTTP 200。未启用 2FA 的账号因此可从临时会话控制转为持久账号控制。已启用 2FA 的账号仍受到第二因素登录限制，此发现不等同于绕过 2FA。

建议：签名与邮箱换绑拆分；换绑先验证当前密码，启用 2FA 时验证第二因素；验证新邮箱所有权后再切换恢复地址；向旧邮箱发出变更提醒。敏感操作应在事务内重新确认执行会话仍有效。

验收：仅凭会话不能改变恢复邮箱；错误密码/第二因素、过期会话均不改变账户；未验证新邮箱不能替换原恢复渠道。

### F02 / P1：已发往旧邮箱的重置链接在换绑后仍可使用

位置：`internal/store/notify.go:350`、`internal/store/notify.go:295`。

换绑仅删除 `email_verifications`，没有撤销 `password_resets`。重置令牌消费只检查用户、令牌、有效期和使用状态，没有绑定当时的邮箱或恢复版本。邮件发送前重新核对收件人不能撤回已经投递的链接。

复现结果：先为旧邮箱创建重置令牌，完成邮箱替换，再提交旧令牌，仍可成功修改密码。

建议：成功换绑时在同一账户事务中撤销全部旧重置令牌；重置令牌绑定邮箱或账户恢复版本。检查换绑与令牌签发、消费的并发顺序。

验收：换绑之前签发的令牌立即失效，换绑后的合法令牌正常使用；并发请求不能复活旧恢复渠道。

### F03 / P1：编辑和重新送审不是原子操作

位置：`internal/api/handler_post.go:256`、`internal/api/handler_post.go:268`、`internal/store/moderate.go:49`。

`UpdatePost` 先提交新正文和标题，然后 `SetPostPendingModeration` 才改变可见性。后者自身也包含多次独立写入。编辑内容需要重新审核时，失败或进程中断可能使未经审核的新内容保持公开，正常执行也有两个提交之间的短暂窗口。

复现结果：对“转为 pending”注入数据库错误。编辑接口返回 HTTP 500，但数据库已保存新正文且 `pending=false`；匿名 GET 返回 HTTP 200 并能读取新内容。

建议：版本校验、编辑历史、正文/标题、审核状态、公开计数及业务事件在同一事务中提交；在事务提交后广播最终状态。审核失败应保留原来公开的正文，或以明确的待审修订版本处理。

验收：任一步骤失败不能公开待审正文；并发读取只观察到旧公开版本或完整的新待审状态；计数、经验/积分和搜索可见性一致。

### F04 / P1：举报已结案，但删除失败仍返回成功

位置：`internal/api/handler_report.go:91`、`internal/api/handler_report.go:99`。

处理“删除”时先把举报标为 resolved，再执行删除；查询楼层和删除失败被忽略。举报结果通知也可能先于实际治理结果产生。

复现结果：注入删除失败后，接口返回 HTTP 200，举报 `status=resolved`，但帖子 `deleted=false`，违规内容仍存在。

建议：举报状态锁定、权限范围复核、内容删除、相关计数和处理结果通知一起提交。删除失败时保留 open 状态并返回错误；对帖子已被其他管理员删除的情况定义明确的幂等结案语义。

验收：响应、举报状态、帖子状态和反馈通知保持一致；失败可重试，多管理员并发处理不会产生假成功。

### F05 / P2：临时待审会永久消耗尚未投递的订阅事件

位置：`internal/store/community_relations.go:276`、`assets/db/migrations/009_community_relations.sql:118`。

订阅任务发现帖子不公开时直接将事件设为 completed；之后重新通过审核，触发器使用 `ON CONFLICT DO NOTHING`，旧事件不会恢复。它混淆了“暂时不可投递”和“投递已完成”。

复现结果：用户事先订阅版块；新主题发布后在 worker 处理前进入待审；worker 运行后，再通过审核并运行 worker。用户通知数量为 0，事件却是 `completed=true`，此前没有投递记录。

建议：区分暂停、已投递和终止状态。重新公开时恢复未完成投递，继续利用用户+帖子投递回执去重，避免给已通知的人重复发送。

验收：未收到通知的原订阅者在重新通过审核后收到一次；已投递用户不重复；后订阅用户不补发历史通知；取消订阅、屏蔽权限及静音仍按既定规则处理。

### F06 / P2：合法长中文帖不能保存为草稿

位置：`internal/api/handler_interact.go:79`、`internal/api/handler_post.go:33`。

发帖限制是 30000 个 Unicode 字符，草稿限制却是 40000 字节，两个相邻流程的容量不一致。

复现结果：15000 个汉字的正文通过发帖内容校验，但草稿保存返回 HTTP 413，因为正文为 45000 字节。实际效果是长帖可以提交，但自动保存提前失效。

建议：发布、编辑和草稿共用正文字符限制；HTTP 请求体仍保留独立的合理字节上限。前端提示与后端校验采用同一口径。

验收：中文、英文、混合字符及表情在同一内容长度规则下，都能先保存草稿再发布；超长时返回一致的校验信息。

## 需明确的产品规则

这些是当前已经明确记录的实现边界，不混入上述 6 项缺陷数量。

1. **称号是否严格“曾经达到就授予”**：当前是评估时满足即授予，授予后不随计数下降撤销。短暂达标但处理前取消，不保证授予；与严格的历史事件成就不同。见 `docs/TITLES.md`。
2. **撤销与恢复后的奖励**：当前取消点赞/采纳、删帖或重新待审会按原规则冲回；同一来源恢复后不再次发奖。这样可以防反复领取，但合法恢复的用户也不会自动恢复原奖励。需在运营文案和人工补偿流程中明确。
3. **2FA 遗失恢复**：当前支持恢复码，不支持可信设备、管理员代关或绕过第二因素的邮件恢复。验证器和恢复码同时丢失时没有自助恢复入口。
4. **积分消费**：账户和流水已实现，冻结只是预留字段；悬赏的冻结、结算、退款尚未实现。投票、签到、排行榜也仍是后续功能。
5. **注销**：保留不可变账本和允许用户退出社区需要共同设计，不能依赖直接删除有业务数据的用户行。

## 发布运维流程：静态发现，未演练

1. **发布流水线会跳过主要数据库测试**：`.github/workflows/release.yml:14` 只运行 `go test ./...`，没有准备隔离 PostgreSQL 或设置测试 DSN；`internal/store/store_test.go:27` 在未设置 DSN 时直接成功退出，API/迁移测试也会跳过。CI 绿色不能证明业务链路和迁移通过。建议将隔离数据库回归设为发布必需检查。
2. **迁移缺少全流程锁与统一版本提交**：`internal/db/db.go:53` 开始重放 schema，编号迁移执行和版本登记分开提交；多实例同时启动可能竞争。建议加入迁移互斥锁，并将单个版本 SQL 与版本登记一起提交。单次 SQL 自身可能隐式成事务，但不等于整个迁移流程原子化。
3. **升级回退不是完整闭环**：`cmd/gobbsctl/main.go:107` 的部分错误分支只恢复二进制文件；`118` 重启失败后未保证重新启动旧版；健康检查使用 `167` 的无客户端超时 `http.Get`，循环外的总时限不能终止单次挂起请求。完整回退还需验证旧服务恢复健康与 schema 兼容性。
4. **搜索修复覆盖不全**：`internal/store/write.go:208` 忽略编辑后的索引错误，`internal/store/search.go:95` 的启动补齐只查 NULL。已存在的旧索引若更新失败，重启也不会修正。本轮没有对此增加故障复现。

本轮未操作线上环境，未重新验证外部 SMTP 收信、HTTPS/代理配置、压测容量、备份还原和多实例部署。
