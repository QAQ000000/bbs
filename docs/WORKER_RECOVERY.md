# Worker 恢复验证

运行 `bash scripts/verify-worker-recovery.sh`。需要 Linux、Go、ripgrep、PostgreSQL 的 `initdb`、`pg_ctl`、`psql`；通过 `RECOVERY_PG_BIN` 指定 PostgreSQL bin 目录（本地默认 `/www/server/pgsql/bin`）。root 运行需已有 postgres 系统用户，普通用户可直接运行。

脚本新建专用临时 PostgreSQL 集群，只监听私有目录中的 Unix socket，不接收现有业务 DSN 或 PGDATA。应用使用无超级用户、建库、建角色权限的测试账号。probe 同时校验数据库、账号、私有 socket 路径和备用连接地址。退出时停止并删除临时集群，日志保留在输出的 `/tmp/gobbs-recovery-results.*` 目录。

## 覆盖范围

probe 使用与 `forumd` 相同的 `RunBackgroundWorkers` 启动入口，共享 20 个连接的池，实际并行运行成长、称号、版块统计、搜索、订阅、邮件和周期快照任务。每个测试使用一个作者、一个订阅者、一个主题和一条回帖，以及一项自动称号；通过真实 store 写入产生派生任务，不以启动全量重建或直接消费循环代替 Worker 恢复。

下列六个故障点分别执行「事务处理中 SIGKILL → 新进程启动」与「事务处理中数据库 immediate stop → 同一 Worker 进程重连」两种场景，共 12 项：

| 目标 | 已完成业务写入后的暂停点 | 回滚及恢复后验证 |
| --- | --- | --- |
| 搜索 | 删除已处理的索引事件前 | 故障事务的索引与事件删除一起回滚；恢复后两篇正文均可搜索，队列排空 |
| 版块统计 | 删除已处理的统计事件前 | 统计及任务保留一致；最终 1 个主题、2 篇帖子 |
| 成长/积分 | 删除发帖成长事件前 | 经验、积分账户、两套流水和任务同事务回滚；恢复后经验 7、积分 2，两类奖励各只有一份 |
| 称号 | 自动授予审计记录插入前 | 已写入的称号资格回滚，原有事件保留；恢复后 1 个自动称号、1 条授予日志，历史回填任务完成 |
| 订阅 | 投递后的游标/完成状态更新前 | 通知、邮件任务、去重回执与游标整体回滚；恢复后收件人收到 1 条站内通知，对应 1 个邮件任务 |
| 邮件 | SMTP 成功返回后、写入 sent 状态前 | 已提交领取租约保留；恢复后原任务 sent、尝试次数 2；本地 SMTP 实收两份，Message-ID 相同 |

## 执行与断言

1. 用 `-race` 执行全部迁移测试、搜索 SQL 失败重试测试、现有邮件 API 测试及 probe/SMTP 夹具测试；数据库测试出现跳过或失败即停止。
2. 每个场景重置独立测试库的 schema，启动只监听 `127.0.0.1` 随机端口的 SMTP 夹具进程，生成业务数据。SMTP 进程独立于 Worker，在 Worker 强杀和数据库重启期间持续记录收件凭据，不读取真实 SMTP 账号。
3. 测试触发器先持有特定 advisory transaction lock，再执行 `pg_sleep`。观察 `pg_stat_activity` 的等待状态并联合 `pg_locks` 确认指定故障正在事务内发生，之后才注入强杀或断连。
4. 强杀后只终止本次临时集群内的遗留连接。断连场景让原 Worker 在数据库停机期间保持存活，恢复数据库后仍检查相同 PID。先验证无部分提交，再解除触发器。
5. 等待所有被校验队列处理完成，同时核对搜索结果、计数、奖励流水、称号授予、订阅去重及实际 SMTP 收件。恢复后重新投递原成长事件、称号重算事件和订阅事件，保留原始成长规则/事件时间，验证幂等性。
6. Worker 和 SMTP 正常退出后再检查一次最终持久状态；每个场景保留 Worker 日志、断言结果、SMTP 收件记录、数据库启停记录。所有进程均使用 race 构建，优雅退出失败也使测试失败。

称号断言按原始事件 ID 确认未丢失，允许并行成长 Worker 合法新增称号重算事件。非邮件专用故障也可能恰好中断邮件处理，因此其 SMTP 断言允许符合任务尝试次数的重复收件，不将正常的至少一次投递误判为事务重复执行。

### 邮件边界

SMTP 接收和数据库标记成功无法组成一个事务。这个测试刻意制造「对方已收到邮件，数据库还不知道」的窗口，验证恢复后的**至少一次投递**，不承诺用户邮箱只出现一次。稳定 Message-ID 便于追踪，也不保证邮件服务商去重。

生产邮件租约仍为 2 分钟。为避免 12 项演练反复等待，在邮件专用场景确认遗留租约状态后，**只修改临时测试库的一条 lease_until 为过去时间**，模拟租约到期，再让实际 Worker 自行领取。不把这一步记为真实等待两分钟的时钟边界测试。

### 尚未覆盖

- 这个脚本独立运行，尚未纳入 GitHub 工作流；本地通过不等于远端 CI 已通过。
- 周期快照 Worker 虽由共享入口启动，但没有对其注入专门故障、验证小时级重试或快照刷新时效。
- 不覆盖完整 HTTP 服务生命周期、外部 SMTP 服务/送达/退信、网络黑洞、备份恢复、大积压与持续容量。
- 两秒停机恢复与小数据事务回滚不能替代持续负载下的背压、队列隔离和生产验收。

schema 17 包含 `forum_stat_events`、`search_index_events` 和 `analytics_snapshots`。迁移测试直接执行编号 SQL 后再重放完整 schema，防止 schema.sql 提前建表掩盖缺失的编号迁移。

## 扩展演练记录（2026-09-27）

在 Go 1.25.14 / PostgreSQL 18.0 的独立临时集群完整运行新脚本成功，证据为 `/tmp/gobbs-recovery-results.T8l0s0`。

- 六类故障点 × 强杀/数据库停机，共 **12 项场景全部通过**；每项在恢复后、事件重放后及所有进程退出后分别校验，合计 36 次最终状态校验。
- 前置回归：迁移 19 项（含子测试 22 项）、搜索 SQL 重试 1 项、邮件 API 8 项、probe/SMTP/加密夹具 5 项，共 33 个顶层测试、36 项含子测试，无失败、无跳过，均启用 race。
- 两项邮件专用场景均确认一个持久任务被领取两次、本地 SMTP 收到两份，Message-ID 不变；其他十项场景各收到一份。成长与积分流水、称号授予及站内通知没有重复。
- 第一轮发现称号事件总数断言过严：并行成长处理会追加合法重算事件。改为检查原始事件 ID 均仍存在后，完整矩阵重跑通过；这不是业务队列丢失或部分提交。
- 脚本正常退出，临时数据库、Worker 和 SMTP 进程已清理；没有替换论坛程序、重启常驻数据库或联系外部 SMTP。

本次为测试夹具和故障验证扩展，没有改变生产任务调度策略或数据库 schema；未重新运行完整后端门禁、持续容量测试或远端 CI。生产背压/隔离、周期快照时效仍按后续工作单独验收。
