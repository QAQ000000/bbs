# 论坛常用基础功能核查

核查日期：2026-09-06。对象为当前工作区 Go API 源码，包含尚未提交的任务称号功能。结论：中小论坛的账号、内容、互动和治理主干已具备，但不能认定常用功能和用户操作流程全部齐全。

## 1. 核查边界

- 以已注册路由、处理函数、数据库结构和调用链为依据，README/ROADMAP 的旧完成标记仅作为线索。
- 当前源码为 schema 8、API 后端；未发现 Nuxt 工程或 package.json。浏览器页面、编辑器、SSR、HTML/Markdown 输出、站点地图等仍待前端接入。
- 只读检查当前本地网站的 `/api/status`：DB up、schema 5。旧版网站不能用于证明当前源码的前端功能已完成。
- 两个具体问题在独立 `gobbs_test_` 数据库中用临时 Go 测试复现，未修改业务代码，未操作业务库。
- 本轮不是所有功能的端到端验收；没有重新验证 SMTP 实际收信、浏览器体验、备份恢复和容量性能。上一轮已有的回归测试不代表覆盖了本轮新增发现的边界场景。

## 4. 已复现的两个缺陷

### F01：收藏漏报新回复

位置：`internal/store/community.go` 的 UnreadFavorites 和 FavoritesOfUser（约 40、58 行）。代码比较 `t.post_count > last_floor`，把剩余楼层数量与单调增长的楼层编号相比较。

复现步骤：主题有 1、2、3 楼，用户收藏并读到 3 楼；删除 2 楼后新增 4 楼。当前剩余三条楼层，但新回复位于 4 楼，接口返回 `lastFloor=3, postCount=3, hasNew=false`。期望 hasNew=true。

建议按“当前用户可见且楼层号高于已读位置的回复是否存在”判断，沿用审核、删除和版块权限过滤。仅改用无过滤的 floor_seq 也会被待审/删除楼层误导。

### F02：待审回复通过后楼主没有回帖通知

位置：`internal/api/handler_admin_moderate.go` 的 adminModeratePost（约 194 行）。通过审核只调用 notifyMentions，没有调用普通发帖路径已有的 notifyReply。

复现步骤：用户 A 创建主题，用户 B 的回复进入审核且未 @ A；管理员通过回复，API 返回 200，回复公开可见；A 的该回复通知数量为 0，期望为 1。

建议统一“内容首次公开后”的通知入口，同时核对主题审核后的 @ 通知、重复审核/重新送审去重，避免补修时造成重复通知。

两个临时测试按正确预期断言并失败，属于成功复现缺陷，不是通过回归。测试通过 Go overlay 临时注入，未加入仓库，也未执行修复；临时库/角色已清理。

## 5. 尚未实现的可选功能

源码与路由中未发现以下完整业务实现：

- 用户私信、会话收件箱。
- 关注/粉丝、用户屏蔽或个人黑名单。
- 主题标签、版块内主题分类、投票帖、悬赏帖、活动帖。
- 连续签到、签到日历、排行榜；当前“每日活跃”不等同于签到产品。
- 第三方登录、2FA、邀请注册。
- 付费会员、积分兑换、付费附件、插件体系。

这些不是所有论坛都必须有。通用讨论社区可优先做标签、屏蔽和订阅；问答社区可在采纳基础上考虑悬赏；不要为了清单完整一次引入全部业务。

## 6. 建议顺序

1. 修复 F01/F02，补充对应回归；它们是已有功能的实际行为错误。
2. 完善通知中心，并把审核、采纳、等级和称号事件接入；补本人待审内容、草稿标题、具体楼层回复/跳转。
3. 建立 Nuxt 前端，完成主流程联调；完善 DTO 状态与 OpenAPI/前端类型，避免前端自行推算。
4. 按定位增加标签、订阅、屏蔽和私信。签到、投票、排行、商业化放在明确需要之后。

以上是功能完整性建议，不替代上线前独立的部署、邮件投递、备份恢复和容量验证。
