## 已实现

| 成长与称号队列 | 分别每秒启动一轮、最多连续 10 个小事务，批次间检查耗时和连接池使用量，繁忙时让出资源 |

新增四个部分索引，仅覆盖未删除、未待审内容：

- `threads_public_latest_idx`：全站最后回复时间及 ID 倒序。
- `threads_public_new_idx`：版块普通主题按创建时间及 ID 倒序。
- `threads_public_author_idx`：作者主题按最后回复时间及 ID 倒序。
- `posts_public_created_idx`：公开楼层按创建时间及主题 ID，支持日期范围统计。

## 请求与统计快照

普通登录请求先通过一个 SQL 读取当前会话和用户；设备活动记录未满一分钟时直接省略写入，超过一分钟仍使用数据库条件更新，防止重复刷新。会话过期、撤销及用户封禁每次查询都重新判断。会员配置、会员状态、禁言、当日额度、版主管辖和全部版块 ID 在另一个 SQL 快照中读取；额度继续提供给 GET 权限预览，写入仍使用原事务预占及失败退款逻辑。

安装状态已初始化且无需更新设备活动时，`GET /api/v1/site` 的普通登录请求执行 3 次数据库访问（会话/用户、站点设置、会员访问范围），原来为 9 次；游客执行 2 次，原来为 3 次。其他接口仍需执行自身业务查询，不能按这两个数字推断全部接口的成本。

首页 `/api/v1/home` 仅缓存各版块的公开主题数、楼层数、今日和昨日楼层数，以及全站会员数。单进程只保留一份快照，并发刷新共享一次查询；快照不含标题、正文、用户名或授权信息。有效期从开始查询时起最多 5 秒，并在数据库时区的午夜提前失效。过期刷新失败返回错误，不无限续用旧数据；等待者可独立取消，首个请求取消后其他等待者可重新发起刷新。

每次首页请求仍实时读取分类和版块资料，按当前可见版块汇总数字。因此权限撤销、版块删除不会因为统计缓存重新暴露资源；公开内容转待审后，其数字可能滞后数秒，但最后回复和主题内容仍按实时状态过滤。首页版块 `todayCount` 与 `stats` 取同一快照，版块自身 `threadCount` / `postCount` 读取版块统计字段；当前默认异步发布时，这些字段由 Worker 更新，具有延迟。独立版块、版块列表及后台统计接口未启用此首页缓存。

## 后台消费预算

成长和称号 worker 仍独立运行，每批分别最多 100 和 50 个事件，继续使用原事务锁及事件顺序。每秒触发后最多执行 10 批；每批开始前检查整轮是否已耗时 250ms，以及共享池已借出连接是否达到最大值的 75%。任一条件满足即停止追加批次，下一秒再试；空队列或本批失败也结束当前轮。

250ms 是批次之间的软预算，不会拆开已开始的事务。单轮数据库上下文继续最多 10 秒，进程退出时取消并等待两个 worker 结束。连接池检查用于退让，不能预留连接或保证前台延迟；持续高负载时队列仍可能积压。理论调度上限为成长 1,000、称号 500 个事件/秒，实际受规则复杂度、锁竞争和事务耗时限制；称号历史补发任务另有每批用户数限制。

## 主题游标分页

原 `page` 分页不变。最新主题时间线可选择：

```http
GET /api/v1/threads?pagination=cursor
GET /api/v1/threads?pagination=cursor&forumId=1
GET /api/v1/threads?pagination=cursor&forumId=1&cursor=<nextCursor>
```

```json
{
  "data": {"threads": [], "stickies": []},
  "meta": {"pagination": "cursor", "pageSize": 20, "hasMore": false, "nextCursor": ""}
}
```

每页数量沿用 `threadsPerPage`。只支持默认最后回复排序，不能传 `page` 或非空 `sort`；无效游标及跨版块游标返回 422。末页 `nextCursor` 为空。

使用 `(last_post_at,id)` 边界和多读取一条的方式判断后续页，不执行 `OFFSET` 或精确总数查询。版块模式把置顶内容单独放入 `stickies`；全站模式保留原最新主题的包含范围。

游标是公开排序边界的编码，不是授权凭据。每次请求重新验证访问权限，并在 SQL 分页前应用版块、待审和删除过滤。相同时间戳以 ID 排序，防止静态数据翻页重复。

时间线不是数据库快照：期间发生回复的主题会移到前面，连续翻页可能不再遇到它，客户端刷新第一页可获取最新状态。

## 超时和连接池

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `FORUM_DB_MAX_CONNS` | 20 | 每进程最大连接数，1–1000 |
| `FORUM_DB_MIN_CONNS` | 2 | 每进程最小连接数，0–最大值 |
| `FORUM_API_TIMEOUT_SECONDS` | 15 | 普通 `/api/` 接口的执行时限 |
| `FORUM_UPLOAD_TIMEOUT_SECONDS` | 60 | 上传执行时限及个人导出查询上下文时限 |

运行参数修改后重启。超时非正数回退默认值；不合法的数字文本沿用环境配置解析的默认值策略。非法连接池大小组合使启动失败。这里的池大小由应用参数控制，覆盖 DSN 中对应的池大小选项。

普通 API、上传使用标准库 `http.TimeoutHandler`，返回 JSON HTTP 503、错误码 `REQUEST_TIMEOUT`，并取消上下文中的 SQL 执行和连接等待。客户端取消请求也向数据库传播。

SSE 和 `/uploads/` 等媒体路径保持原流式行为；个人导出避免额外响应缓冲，只限制上下文中的数据库工作，不保证在时限内中断已经开始的网络传输。超时不能撤销已提交事务；非幂等写入不应直接自动重试，应先查询实际状态。

前台与后台任务共用池。多实例的最大连接数需要合计，并为迁移、运维和其他应用预留容量。增加连接数不能消除同一主题/版块行锁的串行等待。

## 监控

`GET /api/v1/admin` 沿用仪表盘权限，新增 `data.databasePool`：

| 字段 | 含义 |
| --- | --- |
| `max` / `total` / `acquired` / `idle` | 最大、已建立、已借出、空闲连接数 |
| `acquireCount` | 本进程累计成功获取连接次数 |
| `acquireDurationMs` | 累计成功获取连接耗时，包含普通获取，不只是排队 |
| `emptyAcquireCount` | 池为空而发生的获取次数 |
| `canceledAcquireCount` | 获取连接时被取消的累计次数 |

`forumd` 每 30 秒记录一次 `db pool`，并用最多 2 秒的查询采样当前数据库、当前数据库用户的 `Lock` 等待会话。无读取权限或池饱和等导致采样失败时记录 `db lock sample unavailable`。这是瞬时采样，不能覆盖每一次短暂锁等待。

应用池中的 SQL 持续至少 500ms 时记录 `db slow query`，获取连接至少 100ms 时记录 `db connection wait`。慢查询包含 `queryHash`、`durationMs`、失败标记和 PostgreSQL SQLSTATE，不记录 SQL 原文、绑定参数或数据库错误详情。查询耗时包含结果集被调用方消费的时间。

`queryHash` 是 SQL 文本 SHA-256 的前 8 字节十六进制，不等同于 `pg_stat_statements.queryid`。需要 SQL 级排序分析时，可另外启用 PostgreSQL 的 `pg_stat_statements`，结合 `EXPLAIN (ANALYZE, BUFFERS)` 分析。当前代码不会自动安装数据库扩展。

## HTTP 与 SSE 压测方法

测试入口为 `internal/api/load_test.go` 中的 `BenchmarkForumTraffic`。只能指定专用、可丢弃且以 `gobbs_test_` 开头的数据库，测试会重建该数据库的 public schema：

```bash
FORUM_TEST_DSN='<isolated-test-dsn>' FORUM_TEST_ASYNC=1 FORUM_REQUIRE_TEST_DB=1 \
  go test ./internal/api -run '^$' \
  -bench '^BenchmarkForumTraffic$' -benchtime=1x -count=1 -timeout=6m -v
```

测试生成 10,000 个主题、50,000 条楼层，并启动真实本地 HTTP 监听。读取流量均分首页、主题游标列表、主题楼层、主题详情、站点信息，半数工作线程携带真实用户会话；写入使用真实会话、CSRF 和普通会员发帖权限。测量包含订阅、经验、称号 worker；经验与称号每批分别最多 100 和 50 个事件，第二轮基线每秒仅处理一批，第三轮直接调用服务使用的 `RunMemberWork`，采用上文的连续消费预算。

当前夹具使用 `Server.RunBackgroundWorkers`，与 `forumd` 共用经验、称号、搜索、版块统计、订阅、邮件和分析快照任务启动/退出逻辑。另启动浏览计数与数据库监控；邮件发送关闭，邮件维护任务仍运行。`FORUM_DB_MAX_CONNS`/`FORUM_DB_MIN_CONNS` 通过 `config.FromEnv` 实际传给连接池；不启用异步 Store 时 benchmark 直接失败。日志输出实际池大小、异步状态、数据量和 Worker 清单。普通 API 单项回归仍保留同步夹具，避免引入自动消费干扰故障注入。

写入完成后等待派生队列自然清空，检查新回帖搜索词命中和版块计数；不会调用同步校准掩盖 Worker 失败。收尾验证搜索、版块统计、经验、称号、公开订阅和邮件任务无积压，并确认积分与站点快照已生成。预置 50,000 条正文并未构造完整中文搜索索引历史，因此此 benchmark 不作为搜索查询容量测试。

本地可以运行 `FORUM_DB_MAX_CONNS=50 FORUM_DB_MIN_CONNS=5 bash scripts/verify-local-backend.sh load`，自动新建、清理独立 PostgreSQL 集群并保留日志。仍为短测，用于校验夹具和提供基线；30 分钟及 2 小时持续负载、CPU/磁盘采样和告警需另行执行。

同主题和同版块写入各 160 次，检查最终公开楼层及版块计数。100 条 SSE 连接分别模拟独立客户端 IP，接收 20 次主题测试事件及至少一次心跳；同时发起 400 次 HTTP 读取。另创建 500 个订阅者，测量站内通知生成耗时，并观察事件队列清空时间。

HTTP 分位数包含从发请求到读完整个响应的时间，RPS 使用总请求数除以场景持续时间。池指标来自同一共享连接池，包含同期后台任务及 SSE；`emptyAcquires` 是发生等待的连接获取次数，不是失败请求数。SSE 延迟从发布测试事件到客户端读取该事件，包含重新鉴权。预置大表数据时仅在夹具事务内关闭业务触发器，开始测试前恢复；测量阶段的写入执行完整业务逻辑。

这是本机短时、固定并发、收到响应后再发下一次请求的测试，无客户端思考时间。压测进程与 PostgreSQL 共用 WSL2 主机（8 个逻辑 CPU，AMD Ryzen 5 5500；PostgreSQL 18.0，Go 1.25.14），应用池最大 20、最小 2 个连接。未经过 Nginx、TLS、外部网络，也未发送真实 SMTP 邮件；未建立大量历史通知或复杂称号规则。性能测量不启用 `-race`，数据竞争检测由独立回归承担。

## 剩余瓶颈

- 常规鉴权已经合并，100 并发仍可能出现连接池排队；需要结合业务查询、数据库 CPU、I/O 和锁等待评估池大小。
- 首页统计改为最多 5 秒复用，但刷新和后台精确统计仍需扫描；百万级数据下仍需评估按版块增量汇总。
- 热门主题的楼层分配和计数仍持有主题行锁；版块统计已异步，但消费者及审核重算仍可能争用主题或版块锁，需要持续负载验证。
- SSE 现在每次重新鉴权仅一个 SQL，但总工作量仍随连接数乘以事件频率增长。
- 订阅每批仍需锁定主题；50 人批次与批量写入缩短占锁过程，但未验证十万订阅者的扇出。
- 经验、称号队列已支持有界连续消费，但每类队列的事务仍串行执行；持续繁忙、复杂称号规则和大规模后台预览尚未完成容量验证。
- 其他列表的深分页、搜索去重上限及大规模相关性排序。
- 百万级数据、长时间持续写入、慢客户端、资源占用峰值和故障恢复仍未完成容量验证。当前结果不能推算最大在线人数，也不是生产容量承诺。
